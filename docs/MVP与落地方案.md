# JoyMaaS 文档产品 — MVP 与落地可行性方案

> 汇报底稿 · Leah · 2026-08-15
> 上游：[[JoyMaaS文档产品构想]] · 调研：[[2026-08-15_MaaS文档站竞品调研_8家]]

---

## 〇、承接构想的一句话

[[JoyMaaS文档产品构想]] 讲清了立意：**对 JoyMaaS 这种平台，控制台很轻，文档是用户使用产品过程里很重要的一环，值得当成产品的一部分认真做。** 本文只回答一件事——**怎么用最小投入先把这件事验证成立、再落地**。

---

## 一、MVP 只为验证两个假设

老板不会为"完整闭环"买单，他要看**最小投入能否证明这事成立**。MVP 只证明两点：

| # | 假设 | 风险 | 怎么证明 |
|---|------|------|------|
| H1 | 新文档范式确实比旧帮助中心好 | 低（看得见） | 独立现代文档站 + 集成视角内容 + Agent 友好，直接对比旧站 |
| H2 | 文档能反哺、能自我进化 | 高（要验证） | 跑通**一个**反馈闭环，把"文档自我进化"从 PPT 变成能演示的东西 |

> H1 证明"值得换"，H2 证明"这不是普通文档站、有独有价值"。两个都成，立项理由就完整。

---

## 二、MVP 范围：做什么 / 不做什么

### ✅ 做（4 项）

| 模块 | 内容 | 对应假设 |
|------|------|------|
| **1. 独立文档站** | 用开源框架搭一个现代文档站，选一个模型 + 一条完整**集成链路**做样板（快速开始→调用代码→API 参考→排障） | H1 |
| **2. 集成视角内容（不重做模型展示）** | 模型卡片/价格/能力这些"选型展示"由**产品前台元数据**已经在做，文档不重复建；文档专攻"怎么调用"——调用代码、API 参数、限流、错误码、SDK。仅**复用元数据**生成 Agent 要的模型清单（llms.txt / API 参考里的模型枚举），不做对外展示页 | H1 |
| **3. Agent 友好三件套** | llms.txt + 页面 .md + Copy page 菜单（"复制为 Markdown / 在 AI 中打开"）。MCP 列 P1 | H1 |
| **4. 零结果搜索 → 自动写草稿** | 搜索埋点 → 零结果报表 → 达阈值自动触发大模型生成草稿 → 进人工审核队列 | H2 |

### ❌ 不做（划清边界，避免摊大）

- 停留时间的"语义解读推送设计" → MVP 只**采集 + 看板观察**，不做自动推送
- 信息变更自动传播 → 技术最难，留验证期后 POC
- 全量文档迁移 → MVP 只做**一个模型的样板链路**，跑通再铺量
- 多语言、SDK 多语言自动生成 → 后续
- 可视化 WYSIWYG 编辑器 → MVP 先 docs-as-code（Markdown + Git），编辑器 P2

## 三、落地可行性：技术路线

### 整体架构（三层）

```
┌─────────────────────────────────────────────┐
│  前台：独立文档站（开源框架自部署）               │
│  Web 页 / llms.txt / .md / Copy 菜单           │
└──────────────┬──────────────────────────────┘
               │ 消费信号（搜索、停留埋点）
               ↓
┌─────────────────────────────────────────────┐
│  中间层：文档服务 + 智能运营                     │
│  · 模型数据同步（复用产品前台元数据，仅出 Agent 清单）│
│  · 搜索埋点采集 + 零结果检测                     │
│  · 大模型生成草稿 → 审核队列                     │
└──────────────┬──────────────────────────────┘
               │ 读
               ↓
┌─────────────────────────────────────────────┐
│  数据源：产品前台模型元数据 / OpenAPI spec       │
│  （元数据后台是唯一数据源，文档只订阅、不重复维护）  │
└─────────────────────────────────────────────┘
```

### 技术选型（建议，待与技术团队对齐）

| 层 | 选型方向 | 说明 |
|----|------|------|
| 文档站框架 | 开源静态文档框架（如 Docusaurus 类） | 自带 Markdown/MDX、搜索、多版本；社区成熟 |
| 部署 | 京东内网自部署 | ⚠️ Mintlify/Fern 是境外 SaaS，因内网/合规**不能直接接**，只复用其范式和开源件 |
| llms.txt/.md | 构建流水线生成 | 发布时自动产出，标准化能力 |
| 模型数据 | 复用产品前台模型元数据 | 只为出 Agent 清单（llms.txt/API 枚举），不重做对外展示页 |
| 搜索 | 开源搜索件 + 埋点 | 埋点记录 query + 是否命中 |
| 草稿生成 | 调 JoyMaaS 自家模型 | 零结果 query → prompt → 草稿 |

> **"复用"= 复用范式 + 开源件，不是接别人线上服务；业务智能层要自己写代码。**

## 四、分期路线

| 阶段 | 目标 | 内容 | 里程碑 |
|------|------|------|------|
| **P0（MVP，6-8 周）** | 证明 H1+H2 | 独立文档站 + 集成视角样板链路 + Agent 三件套（llms.txt/.md/Copy）+ 零结果闭环 | Time-to-first-call 基线建立；能演示零结果→自动写草稿 |
| **P1（验证后）** | 铺量 + 补 Agent 能力 | 全量模型接入、文档 MCP server、内嵌 AI 问答（Ask JoyMaaS）、Playground | 覆盖主要模型；Agent 可直连；文档满意度 ≥ 85% |
| **P2（成熟期）** | 完整智能闭环 | 停留信号推送产品/设计、信息变更自动传播（POC 通过后）、可视化编辑器、SDK 多语言自动生成 | 三个反馈闭环全通；手写量降至约 10% |

> **P0 Agent 三件套必须进来**（llms.txt/.md/Copy page）。这是 JoyMaaS 区别于火山/腾讯的入场券，且成本极低（发布流水线加一步）。推到 P1 只会让 MVP 退化成"一个好看点的普通文档站"，H2 故事就弱了一半。MCP 因工程量稍大，放 P1。

## 五、资源与周期（粗估，待细化）

> 以下为量级判断，非承诺；需与技术团队评估后确认。

| 角色 | 投入 | 干什么 |
|------|------|------|
| 产品（Leah） | 牵头 | 信息架构、内容规划、闭环设计 |
| 前端 | 1 人 | 文档站搭建、集成样板页、Copy/Agent 能力 |
| 后端 | 1 人 | 模型数据同步、搜索埋点、草稿生成 pipeline |
| 内容 | 兼职/AI 辅助 | 样板链路内容 + 审核 AI 草稿 |

**P0 周期粗估：约 6～8 周**（框架搭建 2 周 + 集成样板链路 + 元数据订阅出 Agent 清单 2 周 + Agent 三件套 1 周 + 零结果闭环 2 周，含联调）。

## 六、风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| 元数据无对外可读出口 / 字段不足以出 Agent 清单 | 中 | 立项前先摸清元数据后台有没有 API 出口，确认字段够不够生成 llms.txt 模型清单 |
| 零结果自动生成的草稿质量差 | 中 | MVP 只到"进审核队列"，人审后发布，不自动上线 |
| 开源框架与京东内网部署/权限体系不兼容 | 中 | 选型前做部署验证 |
| 与现有帮助中心的关系（替换 or 并存） | 中 | 先并存，MVP 做增量样板，验证后再谈迁移 |
| 智能层被质疑"技术做不出来" | 低（MVP 已规避） | MVP 只选风险最低的零结果闭环，难的留 POC |

---

## 七、成功指标（MVP 验收）

**核心：两个可量化的指标，不用主观打分。**

| 指标 | 目标 | 说明 |
|------|------|------|
| **Time-to-first-call（首次成功调用耗时）** | 对比旧站有显著下降 | 开发者从看文档到跑通第一个 API 调用的时间，是文档质量的黄金指标 |
| **搜索满足率（1 - 零结果率）** | 零结果率下降可量化 | 反馈闭环跑起来后，零结果数量应持续下降 |

**H1 验收**：样板集成链路上线，Agent 清单（llms.txt 模型枚举）由元数据 100% 自动生成（零人工维护）；llms.txt/.md/Copy 三件套可用；Time-to-first-call 有基线数据可对比。

**H2 验收**：零结果闭环跑通——能演示"系统检测到 N 次零结果 → 自动生成草稿 → 审核发布"完整链路至少 1 个真实案例。

---

## 八、给老板的一句话

**先花 6～8 周做一个模型的样板：一个数据自动生成、对人和 AI 都友好的现代文档站，外加一个"用户搜不到、系统自动补文档"的智能闭环 demo。用最小成本证明"新范式更好 + 文档能自我进化"，成了再铺量、再上更难的闭环。**
