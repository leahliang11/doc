# JoyMaaS 文档后台交互设计 v1

> 目标：让编辑者可以像使用成熟知识库产品一样，完成“组织目录 → 创建文档 → 编辑预览 → 保存草稿 → 提交审核 → 发布后复查”的完整闭环。
>
> 参考：GitBook 的页面树与 change request、Mintlify 的可嵌套导航、Notion 的无限层级页面树。

## 一、核心判断

当前后台已经有文档列表、编辑器、草稿分支、合并请求和审核队列，但交互仍然是“目录展示 + 文档表格”的管理后台，不是编辑者工作台。

主要问题：

1. 目录只有 `section → group → page` 三层，不能继续创建子目录。
2. 目录操作依赖拖拽和隐藏按钮，新增、重命名、移动、删除不够可发现。
3. 创建文档后，文档和目录之间的关系不够明确，未分类文档容易丢失。
4. 编辑器缺少清晰的保存状态、预览、版本、审核上下文。
5. 删除没有回收站/恢复路径；当前只能创建删除 MR，编辑者看不到后续状态。
6. 右侧表格与左侧目录重复展示同一信息，空间利用率低，字体和操作优先级不合理。

## 二、目标信息架构

后台“文档”页采用三栏工作台：

```text
┌─────────────────────────────────────────────────────────────┐
│ 顶部：当前空间 / 搜索 / 待处理变更 / 预览 / 构建 / 账号      │
├──────────────┬──────────────────────────────┬───────────────┤
│ 目录树       │ 文档列表或编辑器              │ 属性/预览      │
│              │                              │               │
│ + 新建       │ 列表：筛选、排序、批量操作     │ 编辑时显示     │
│ 搜索目录     │ 编辑：正文、状态、保存、审核   │ 元数据和大纲   │
│ 无限层级     │                              │               │
└──────────────┴──────────────────────────────┴───────────────┘
```

默认进入“文档工作区”，保留目录树；点击文档后进入编辑器，目录树不消失，避免在列表和编辑器之间来回跳转。

## 三、目录树设计

### 3.1 节点模型

将当前固定三层模型升级为递归节点：

```ts
type DocNode = {
  id: string
  type: 'folder' | 'page'
  title: string
  slug?: string
  children?: DocNode[]
  order: number
  expanded?: boolean
}
```

顶层可以是文件夹或文档；文件夹可以继续嵌套文件夹和文档。发布站点可以把文件夹映射成导航分组，文档映射成页面。

### 3.2 节点操作

每个节点右侧使用明确的 `…` 操作菜单，不依赖“猜悬停”：

- 文件夹：新建子文件夹、新建文档、重命名、移动、复制链接、删除。
- 文档：打开编辑、在新标签预览、重命名（标题和 slug 分开确认）、移动、复制、删除。
- 根目录：新建顶层文件夹、新建顶层文档、刷新。

删除规则：

- 文件夹非空时提示“删除后移入回收站”，默认不直接清空。
- 文档进入回收站，创建删除审核变更。
- 回收站保留 7 天，可恢复原目录和排序位置。

### 3.3 移动与排序

- 拖拽时显示明确的插入线：放入文件夹、放在节点前、放在节点后。
- 拖拽完成立即更新本地树，并显示可撤销 toast；保存目录变更时创建一个导航 MR。
- 支持操作菜单“移动到…”打开树形选择器，作为拖拽的无障碍替代方案。
- 目录排序支持手动排序和按标题排序，两者要明确区分。

### 3.4 创建入口

点击目录树顶部 `+ 新建` 展开菜单：

- 新建文件夹
- 新建文档
- 从模板新建
- AI 生成文档
- 从 OpenAPI 生成接口文档

在某个文件夹上点击 `+` 时，创建文档弹窗默认带入该目录，不允许创建后再猜它应该去哪。

## 四、文档列表设计

列表不是第二棵目录树，而是“当前目录的内容视图”：

- 顶部显示面包屑：`全部文档 / API 参考 / Chat`。
- 支持搜索标题、slug、正文。
- 筛选：状态、作者、更新时间、是否有未提交改动。
- 排序：最近更新、标题、状态。
- 行操作：打开、预览、复制、移动、删除。
- 行内显示状态：草稿、待审核、审核通过、已发布、删除中。
- 批量操作只提供安全动作：移动、提交审核；删除需要二次确认。

右侧表格文字使用高对比正文色，slug 使用等宽字体但不能比标题更抢眼；操作列固定在右侧，图标配 tooltip 和文字菜单。

## 五、编辑器工作流

### 5.1 编辑器布局

```text
┌──────────────────────────────────────────────────────────────┐
│ ← 返回目录  文档标题  [草稿] [已保存]       预览  保存  提交审核 │
├──────────────────────────────┬───────────────────────────────┤
│ Markdown/MDX 编辑区           │ 实时预览                        │
│                               │                               │
│ 工具栏：标题、代码、提示、     │ 与前台样式一致                   │
│ 参数表、步骤、链接、图片       │ 支持桌面/移动预览                 │
├──────────────────────────────┴───────────────────────────────┤
│ 底部状态：最后保存时间 / 分支 / MR / 冲突 / 字数                │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 保存状态

统一使用状态徽标，不再只弹 toast：

- 未修改：已保存
- 输入中：有未保存修改
- 保存中：正在保存…
- 已保存：已保存于 18:42
- 待审核：已提交 MR #123
- 冲突：远端有新版本，查看差异
- 保存失败：重试 / 复制错误详情

自动保存只保存本地草稿；服务端保存仍由显式“保存草稿”触发，避免编辑者误以为已经进入审核流程。

### 5.3 预览与 MDX 组件

组件插入采用命令菜单和 slash menu：

- `/callout` 提示
- `/steps` 步骤
- `/code` 代码
- `/params` 参数表
- `/playground` API 调试区
- `/next` 下一步

插入后可在右侧预览立即看到效果；组件配置提供“表单模式”和“源码模式”，避免只会写 MDX 的用户无法使用。

## 六、审核与发布链路

### 6.1 草稿与线上内容分离

审核的边界不应覆盖所有编辑动作。编辑者在草稿区应能自由创建、修改、移动和删除未发布内容；只有会影响线上读者的变更才进入审核：

- 未发布草稿：保存、重命名、移动、删除均可直接操作，删除进入回收站。
- 已发布文档正文：修改后进入待审核变更，原线上版本保持不变。
- 已发布文档删除：进入删除审核，审核通过后才从线上移除。
- 目录结构：如果只影响草稿区，直接保存；如果改变线上导航，则合并为一次结构审核。

这样既保留 Git/MR 的审计和回滚能力，又避免编辑者为了写一篇草稿被迫反复提交审核。

编辑者始终能看到当前文档的变更上下文：

1. 创建文档：选择目录和模板，生成草稿。
2. 编辑保存：写入同一 draft 分支，不重复创建分支。
3. 提交审核：展示变更摘要、目标目录、影响页面和 MR 链接。
4. 审核中：编辑器只读或允许创建新变更，明确提示不能覆盖审核中的版本。
5. 审核通过：状态变为已发布，显示发布时间和发布构建号。
6. 审核拒绝：显示原因，一键“继续修改”回到同一变更上下文。

右上角增加“待处理变更”入口，按文档聚合，而不是只展示 MR 编号。

## 七、需要补齐的接口

### 7.1 目录

- `GET /api/tree`：返回递归目录树和节点状态。
- `POST /api/tree/nodes`：创建文件夹或空文档节点。
- `PATCH /api/tree/nodes/:id`：重命名、移动、排序、展开状态。
- `DELETE /api/tree/nodes/:id`：移动到回收站并创建审核变更。
- `POST /api/tree/restore/:id`：从回收站恢复。

### 7.2 文档

- `GET /api/docs/:slug/versions`：版本列表。
- `GET /api/docs/:slug/diff`：当前草稿与基线差异。
- `POST /api/docs/:slug/duplicate`：复制文档并自动生成新 slug。
- `PATCH /api/docs/:slug/frontmatter`：单独更新标题、描述、标签、受众。
- `GET /api/docs/:slug/preview`：服务端渲染预览，保证后台和前台一致。

### 7.3 审核

- `GET /api/changes`：按文档聚合变更。
- `POST /api/changes/:id/submit`：提交审核。
- `POST /api/changes/:id/withdraw`：撤回审核。
- `POST /api/changes/:id/reopen`：审核拒绝后继续修改。

## 八、权限和安全

- 编辑者：创建、编辑、移动、提交审核；删除进入回收站。
- 审核者：查看 diff、评论、通过、驳回；不能直接修改正文。
- 发布者：合并审核、触发构建、回滚。
- 所有破坏性操作都有确认和可恢复路径。
- 删除、重命名 slug、移动大量节点必须显示影响范围。

## 九、实施顺序

### P0：先解决每天都会遇到的问题

1. 三栏工作台和固定目录树。
2. 文件夹/分组的新增、重命名、移动、删除。
3. 创建文档时选择目录。
4. 明确编辑器保存状态和审核状态。
5. 列表搜索、筛选、行操作统一。

### P1：完善内容生产体验

1. 无限层级递归树和移动到选择器。
2. 实时预览、组件命令菜单、移动端预览。
3. 版本、diff、撤回审核、继续修改。
4. 回收站和恢复。

### P2：团队化能力

1. 评论和批注。
2. 文档负责人、协作者、权限继承。
3. 批量操作和发布前检查清单。
4. 搜索分析、零结果反馈和内容质量报告。

## 十、验收标准

- 新用户不看说明也能在 30 秒内找到“新建文件夹”和“新建文档”。
- 从目录打开文档、修改、保存、预览、提交审核不丢失上下文。
- 任何文档都能明确看到当前状态和下一步动作。
- 删除后能找到回收站并恢复，线上内容不会被误删。
- 目录层级至少支持 4 层，移动文档不需要编辑 YAML。
- 前台预览和后台预览的标题、提示、代码块、参数表样式一致。
