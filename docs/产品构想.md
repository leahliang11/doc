# JoyMaaS 文档产品构想

> 汇报底稿 · Leah · 2026-08-15
> 关联调研：[[2026-08-15_MaaS文档站竞品调研_8家]]

---

## 一句话

**对 JoyMaaS 这种平台，文档不是产品的附属说明书，而是用户使用产品过程里很重要的一环。** 控制台很轻，用户真正"用起来"的过程——选模型、拿 Key、跑通调用、接进自己的工作流、排障、控成本——主要发生在文档里。所以文档要当成**产品的一部分**认真做：内容大部分自动生成、能被人和 AI 双向消费、并把消费行为反哺回内容生产，形成自我进化的闭环。

> 一句话立住：**对 API 型产品，文档就是半个产品。**

---

## 一、为什么做这件事（先讲清价值，不是"文档旧了要翻新"）

### 竞争现实：模型不占优，体验是我们能赢的地方

先摆一个不回避的事实：**JoyMaaS 作为模型服务平台，手里没有绝对领先的自研模型。** 用户为什么选我们，就不能只押"模型强"。

那能拼什么？拼**用户在我们这里用得顺不顺**：

1. **接入成本低** —— 能不能 5 分钟跑通第一个 API
2. **使用过程顺** —— 知不知道该选哪个模型、怎么调参、怎么处理报错、怎么控成本
3. **能接进自己的工作流** —— API 只是用户工作流里的一个节点，用户最终要把模型能力放进自己的系统/Agent/业务流程
4. **问题能自救** —— 限流、鉴权、计费、上下文异常，不用反复找售前/客服/研发
5. **人和 AI 都能读懂** —— 现在读文档的不只有人，还有用户自己的 AI 助手、开发 Copilot、Agent 编排系统

这五点里没有一条依赖"模型多强"，全是**体验层能做的差异化**。对没有王牌模型的平台，这恰恰是最现实、最能自己掌控的竞争抓手。

### API 型产品的特殊性：控制台很轻，使用成本全在控制台之外

MaaS 和云硬盘、云主机不是一类产品。传统云产品的帮助文档是**售后说明书**：先买产品，再查怎么配，文档是补充。

但 JoyMaaS 的控制台本身很轻——开通服务、创建 API Key、看模型、调接口，点几下就完了。**真正复杂、真正决定用户能不能用起来的事，全发生在控制台外面：**

- 我该选哪个模型？
- 怎么把它放进我的业务系统？参数怎么调？
- 为什么返回慢 / 效果不稳 / 报错？
- 怎么降低调用成本？怎么接 Agent？怎么处理多轮上下文？
- 怎么在生产环境稳定跑？

这些问题不是控制台按钮能解决的，主要靠**文档、示例、工具、智能问答**来解决。所以在这种产品形态里，文档不是附属品——

> **它是用户使用产品的主要界面之一。**

### 现状问题：现有帮助中心承接不了这个角色

现在 JoyMaaS 用的是京东云通用帮助中心。它是为**静态云产品**设计的文档范式，套在 MaaS 上是**范式错配**：

- 样式与内容陈旧、对用户不友好
- 模型信息靠人工维护静态表格 → 模型一多就滞后、口径不一
- 代码不能跑、没有内嵌问答、对 AI 不友好
- 文档是"单向输出"，用户在哪卡住、搜什么搜不到，平台一无所知
- **只把文档当"说明书"，承接不了"帮用户把模型接进业务"这个真正重要的过程**

### MaaS 文档与普通云产品文档的四个结构性差异

| 维度 | 普通云产品文档 | MaaS 文档 |
|------|------|------|
| 内容节奏 | 半年不动 | 每周上新模型、调价、改能力 → 内容是"活"的 |
| 文档角色 | 看完再去控制台操作 | 文档本身就是接口（读到即可试、复制即可接） |
| 用户目的 | 学操作步骤（买→配→挂载，线性） | 选型决策 + 集成 + 调试 + 工作流落地（发散、非线性） |
| 读者 | 人 | 人 + Agent（Cursor/Claude 帮开发者接 API） |

> 结论：不是"把旧文档翻新"，而是要**换一套匹配 MaaS 特点的文档做法，并把文档当成产品使用体验的一部分来对待**。

## 二、新定位：文档是产品使用体验的一部分，不是附属说明书

**旧定位**：文档 = 使用说明书，产品的附属品。

**新定位**：文档是**用户使用 JoyMaaS 过程里很重要的一环**。用户从了解、选型、拿 Key、接入到稳定使用的全过程，很大一部分是靠文档、示例、工具、智能问答走完的。所以文档不该被当成"产品做完之后补的说明"，而应该**当成产品体验的一部分来设计和投入**。

从它实际起的作用看，文档同时在干三件事：

- **销售**：吸引开发者来，降低首次成功调用门槛
- **产品**：让用户用起来，Playground / 内嵌问答 / 复制即可接 / 工作流示例
- **客服**：让用户自助解决问题，少来找人

> **文档是增长杠杆，不是成本中心。** 这是它和普通帮助中心最根本的定位差异。

两点决定了它比"帮助文档"承担得更多：

**一、它承接用户的完整使用路径。** 不是一堆按"产品说明章节"排的静态文档，而是**按用户任务组织**：快速开始、选模型、API 调用、SDK/Prompt 示例、错误码、限流、计费、生产最佳实践、Agent 接入、常见场景解决方案，串成用户能走通的一条路。

**二、它要帮用户把模型接进工作流。** 用户不是为了"调 API"而调 API，而是要把模型能力接进自己的业务（客服系统、内部知识库、研发助手、数据分析、内容生成、Agent 编排）。**API 只是用户工作流里的一个节点**，文档要从"接口怎么调"扩展到"怎么放进你的流程里"——这是传统云帮助文档不做、而 MaaS 用户真正需要的，也是 JoyMaaS 最该做深的地方。

三类读者各有诉求：

1. **对开发者**：文档不只是"看"，是"用"——读到即可试跑、问即可答、复制即可喂给自己的 AI 接入。
2. **对 Agent**：读文档的越来越多是机器（Cursor/Claude 帮开发者接 API）。文档必须机器可读。**JoyMaaS 卖的是模型能力，用户就是拿 AI 来接你的 AI**——这个品类里 Agent 友好不是加分，是入场券。
3. **对 JoyMaaS 自己**：文档是**离用户最近的产品信号采集器**，也是**用户使用障碍的观测台**。用户在哪卡住、搜什么没命中、哪段读得久——都是免费、真实的产品反馈。

## 三、核心：从供给端到消费端的完整闭环

```
           ┌───────────────────────────────────────────┐
           │                                           │
           ↓                                           │
   ① 供给端                                             │
   内容怎么来（核心：少人工）                              │
   · 数据驱动生成（API 参考 + Agent 模型清单）           │
   · AI 辅助生成（指南初稿）                               │
   · 人工兜底（理念/最佳实践）                             │
           │                                           │
           ↓                                           │
   ② 加工与分发                                          │
   一份内容 → 多种形态                                    │
   · Web 页（给人）                                      │
   · llms.txt + .md（给 Agent）                          │
   · OpenAPI（给开发者）                                  │
   · MCP（给 IDE 直连）                                   │
           │                                           │
           ↓                                           │
   ③ 消费端                                             │
   谁在用、怎么用                                         │
   · 选型者 / 开发者 / 排障者（人）                         │
   · Cursor / Claude（Agent）                            │
   · 读到即可试、问即可答、复制即可接                        │
           │                                           │
           ↓                                           │
   ④ 反馈闭环 ★最大亮点                                   │
   消费行为反哺供给                                       │
   · 停留时间 → 产品复杂度信号                             │
   · 零结果搜索 → 自动写文档 ──────────────────────────────┘
   · 信息变更 → 自动传播替换（回到①，自动更新内容）
```

### ① 供给端 —— 内容怎么产生（核心主张：把人从"写"里解放出来）

**写作三分法**——按内容类型分工，把能机器生成的都交给机器：

| 内容类型 | 怎么来 | 手写占比 |
|------|------|------|
| API 参考、请求示例、参数表、Agent 模型清单（llms.txt 枚举） | OpenAPI spec + 复用产品前台元数据 **自动生成** | **0%** |
| 快速开始、集成指南、教程、FAQ、多语言翻译 | AI 写初稿，人审核润色 | **约 20%** |
| 产品定位、场景叙事、踩坑经验、语气风格判断 | 人工撰写（也是最值钱的部分） | **约 10%** |

> **主张：团队精力只花在最值钱的那 10%。** 研发/PM 从"写文档 + 追着更新"里解放，只做"审文档"。Reference 信息密度高但不需要文采，机器最擅长；场景叙事要懂用户、会讲人话，才值得人亲自写。

### ② 加工与分发 —— 写一次，人和机器各取所需

一份源内容 → 同时产出多种形态，不重复维护：
- **Web 页** —— 给人看，好样式、可交互
- **llms.txt + llms-full.txt** —— 给 Agent 导航和 RAG
- **页面 .md 版本** —— URL 加 `.md` 即得纯 Markdown，喂给任意 AI
- **OpenAPI spec** —— 给开发者和 SDK 生成
- **文档 MCP server** —— 让 Cursor/Claude Code 直连检索 JoyMaaS 用法

### ③ 消费端 —— 三类人 + 一类机器，开发者从陌生到上线

**人的旅程（6 步）：**

1. **进来** —— 从官网或搜索引擎落地
2. **Quickstart 跑通** —— 5 分钟复制代码，第一次成功调用，有成就感（核心指标：Time-to-first-call）
3. **Guides 找做法** —— 按"我想做 X"找指南，看多语言代码、参数表
4. **卡住时自救** —— Playground 试调、问 Ask JoyMaaS
5. **集成上线** —— 复制代码到自己项目，跑通业务
6. **偶尔回看** —— 遇新需求再来搜/问（闭环）

**Agent 通道：** Cursor/Claude 读 llms.txt 了解 JoyMaaS 能力 → 自动生成调用代码 → 通过 MCP 实时问 → 拿到准确答案。这是传统云厂文档没有、MaaS 必须有的通道。

| 场景 | 谁 | 在问什么 | 文档给什么 |
|------|------|------|------|
| 选型决策 | 架构师/选型者 | 该用哪个模型？贵不贵？上下文够不够？ | 模型对比/价格/能力由**产品前台**承接；文档提供选型指引 + 无缝跳到集成 |
| 集成开发 | 开发者 | 怎么最快跑通第一个调用？SDK 怎么接？ | Quickstart、可运行代码、Playground、Copy for LLM |
| 排障调试 | 遇到问题的开发者 | 为什么报错/限流/费用对不上？ | 错误码、限流说明、内嵌 AI 问答 |
| Agent 接入 | Cursor/Claude | JoyMaaS 这个接口怎么调？ | MCP / llms.txt / .md 直接读取 |
| **内部消费** | 售前/销售/运营/客服 + 内部 AI | 客户问支持啥模型/怎么计费/能否私有化 | 同一套文档权威作答；内部 AI 直接读 llms.txt/MCP，基于事实源答客户 |

> 关键体验：**读到即可试（Playground）、问即可答（内嵌 AI）、复制即可接（Copy for LLM）。**

### ③.5 内外双服务 —— 一套事实源，内外通吃（P1 愿景）

这份文档不只服务官网外部用户，同时是**公司内部唯一的产品事实源**。它把文档从"官网门面"升级成 single source of truth。

**内部谁在用：**

| 内部角色 | 拿文档干嘛 | 现在的痛点 |
|------|------|------|
| 售前/销售 | 答客户"支持啥模型/怎么计费/能否私有化" | 靠口口相传、翻群、问 PM，口径不一还易说错 |
| 运营/客服 | 写对外材料、答疑、培训 | 自己另攒一套说法，和官网两张皮 |
| **内部 AI** | 售前把文档喂给自己的 AI 助手，客户一问 AI 基于权威文档直接答 | 现在内部 AI 没有可信数据源，容易瞎编 |

**为什么价值大：**
1. **口径对齐** —— 销售说的 = 官网写的 = AI 答的，不再打架。
2. **Agent 能力零成本复用** —— 为外部 Agent 做的 llms.txt/.md/MCP，内部 AI 直接就能用。做一次，内外两拨 AI 通吃。
3. **销售提效挂营收** —— 售前 AI 基于权威文档答客户，成单更快、说错更少。

**必须守住的边界 —— 内容可见性分级：**
"内外通吃"不是"同一站点谁都看"，而是**一套内容源 + 权限分级出口**：
- 公开层 → 官网 + 外部 Agent
- 内部层 → 内网门户 + 内部 AI（含只给内部的：定价底价/折扣、私有化细节、未发布模型、竞品话术）

> ⚠️ 不分级会把内部机密漏到官网。这套"对外/对内"可见性思路，与产品前台元数据后台已在做的"对外字段/对内字段"逻辑一致，可延续。
> 本节属 **P1 愿景**，不进 MVP；MVP 阶段口头讲，用来拔高天花板。

### ④ 反馈闭环 —— 消费反哺供给（旧帮助中心永远做不到的维度）

这是把文档从"成本中心"变成"数据资产"的部分，也是 JoyMaaS 文档最独有的价值：

| 信号 | 怎么用 | 闭环动作 |
|------|------|------|
| **停留时间** | 某块读得特别久 = 这块功能复杂/难懂 | 自动生成信号推给产品/设计："这里可能要优化" |
| **零结果搜索** | N 个人搜了同一个词、没命中文档 | 自动触发 AI 生成这篇文档的草稿 → 进审核队列 |
| **信息变更** | 改了价格/能力/字段 | 自动找到所有提到它的散文档并替换 |

> **主张：文档会自己发现缺口、自己修复、自己进化。**

## 四、后台怎么建设：两层架构 + 复用边界

后台劈成两层，边界回答"接现成 vs 自己写"：

### 底座层（复用成熟范式，尽量少自研）
文档渲染、导航、搜索、样式、llms.txt/.md、Copy page 菜单、OpenAPI→API 参考+Playground、基础埋点、docs-as-code + 可视化编辑。
> 这些已被 Mintlify/Fern 等工具标准化。**复用的是"范式和开源件"，不是别人的线上服务**——因内网/合规，Mintlify/Fern 的境外 SaaS 不能直接接，需用等价开源方案（如 Docusaurus 类）自部署在京东环境。这层投入越少越好，不是创新点。

### 智能运营层（必须自建，JoyMaaS 后台的灵魂）
① 停留时间 → 产品复杂度信号闭环
② 零结果搜索 → 自动写文档 pipeline
③ 信息变更 → 语义级自动传播替换
④ 复用产品前台元数据 → 自动出 Agent 模型清单（llms.txt 枚举 / API 参考模型枚举）；**不重做模型展示页**（那是产品前台的地盘）

> **规律：凡"通用文档能力"→ 复用底座；凡"要懂 JoyMaaS 产品 / 碰 JoyMaaS 业务数据"→ 自建。** 上述四项全在后者，竞品给不了，因为它们是通用工具，不懂我们的产品、不碰我们的数据。这才是值得 JoyMaaS 自己做的部分。

## 五、为什么值得牵头做（给老板的价值主张）

0. **战略层：这是不依赖模型强弱的差异化抓手** —— JoyMaaS 没有王牌模型，但"接入体验 + 使用体验"是可以自己做到更好、且用户看得见的差异点。把体验做到位，用户就愿意试、愿意接、愿意留。**做好文档不只是把说明写清楚，而是在体验层为平台建立竞争力。**
1. **降本** —— 写作三分法：手写量降至约 10%，研发/PM 从"写文档 + 追着更新"里解放，只做审核。
2. **拉转化** —— 文档是获客与留存的核心转化点。Time-to-first-call（首次成功调用耗时）缩短，直接拉动 MaaS 转化。把"成本中心"变成**增长杠杆**。
3. **独有的数据资产** —— 文档成为离用户最近的产品信号采集器与使用障碍观测台，反哺产品设计。这是旧帮助中心永远给不了的价值。

> 给老板可以用这条主线讲：**JoyMaaS 是模型服务平台，控制台很轻，用户真正的使用成本集中在选型、调通 API、接入业务流程和排障上。在这种产品形态里，文档不是产品做完后补的说明书，而是用户使用产品过程中很重要的一环——它直接影响用户能不能跑通、能不能接入、会不会继续用。我们不一定靠模型本身形成差异化，但可以把"接入体验"和"使用体验"做到更好。所以这件事值得当成一个正经产品方向来投入，我想牵头做。**
