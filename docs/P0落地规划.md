# JoyMaaS 文档系统 P0 落地规划（双通道版）

> 本文档取代 `JoyMaaS文档_P0落地规划.md`。核心变更：Git 从"隐藏后端"升级为"权威源 + 双通道输入"，PM/运营用 Web Editor，工程师用 Git/IDE，两条通道写同一份内容。执行者：Claude Code。

---

## 0. 一句话目标

**让 JoyMaaS 文档同时满足三件事**：

1. **人能读顺** —— 现代文档站 + MDX + 白名单组件
2. **AI 能读对** —— 页面 `.md` + `llms.txt` + Copy as Markdown
3. **两种人都能写** —— PM/运营用 Web Editor；工程师用 Git/IDE；两条通道写**同一个 Git 仓库**

## 1. 核心架构（钉死，不许改）

```
                     ┌─────────────────────────┐
                     │  Git 仓库(权威源)       │
                     │  content/**/*.mdx       │
                     │  content/api-spec/*.yaml│
                     └─────────┬───────────────┘
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
     ┌─────────────────┐               ┌─────────────────┐
     │   Web Editor    │               │  Git / GitHub   │
     │  (读写 Git)    │               │  (直接 push)    │
     └────────┬────────┘               └────────┬────────┘
              │                                 │
        PM/运营/售前                          工程师
              │                                 │
              │ Save → auto commit              │ push / PR
              │                                 │
              └────────────┬────────────────────┘
                           ▼
                    审核队列(双入口)
                           │
                           ▼
                    发布 = merge to main
                           │
                           ▼
                     Next.js 构建
                           │
                  ┌────────┴────────┐
                  ▼                 ▼
              人类阅读         Agent 消费
             (HTML 页面)     (.md / llms.txt)
```

**四条不可违反的原则**：

1. **Git 是唯一权威源**：Web Editor 不维护独立数据库，它读写的是 Git。
2. **Web 保存 = 真实 Git commit**：作者 = 登录用户，不能是"bot"。
3. **PR = 审核任务**：工程师提的 PR 自动进审核队列，PM 也能审。
4. **发布 = merge to main**：不管从哪条通道进来，最终都通过 merge 发布。

## 5. 数据模型

### 5.1 MDX Frontmatter

```yaml
---
title: 快速开始
description: 5 分钟跑通第一次调用
slug: quickstart
category: quickstart | models | api | guides | troubleshooting
audience: external | internal | both
tags: [chat, streaming]
updated: 2026-08-23
status: draft | review | published | archived
owner: leah
ai_readable: true
source: manual | openapi                # openapi 表示自动生成,结构化区域只读
---
```

### 5.2 后台状态（PostgreSQL 或 SQLite，P0 用 SQLite）

```sql
-- 审核任务
CREATE TABLE review_tasks (
  id INTEGER PRIMARY KEY,
  source TEXT NOT NULL,           -- 'web' | 'github_pr'
  slug TEXT NOT NULL,
  branch TEXT NOT NULL,           -- 'draft/quickstart-123' or 'pr-45'
  pr_number INTEGER,              -- 仅 github_pr
  submitter TEXT NOT NULL,
  status TEXT NOT NULL,           -- 'pending' | 'approved' | 'rejected' | 'merged'
  created_at TIMESTAMP,
  reviewed_at TIMESTAMP,
  reviewer TEXT,
  comment TEXT
);

-- 编辑会话(用于冲突检测)
CREATE TABLE edit_sessions (
  id INTEGER PRIMARY KEY,
  slug TEXT NOT NULL,
  user TEXT NOT NULL,
  base_commit TEXT NOT NULL,      -- 打开文档时的 Git commit hash
  opened_at TIMESTAMP
);

-- 埋点(P0 也可以先用 JSONL,P1 再迁 DB)
CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  event_type TEXT,
  props TEXT,                     -- JSON
  created_at TIMESTAMP
);
```

## 7. Git 双通道实现细节（P0 核心难点）

### 7.1 Web Editor 打开文档

```
用户点击文档
  ↓
POST /api/docs/open { slug }
  ↓
后端:
  1. git pull(拉最新)
  2. 读 content/<slug>.mdx
  3. 记录当前 HEAD commit hash 到 edit_sessions
  4. 返回 { markdown, frontmatter, base_commit }
```

### 7.2 Web Editor 保存

```
用户点击保存
  ↓
POST /api/docs/save { slug, markdown, base_commit }
  ↓
后端:
  1. git fetch
  2. 检查 main 分支上 base_commit 之后是否有影响 <slug>.mdx 的提交
     - 有 → 返回 409 冲突 + 远端最新内容
     - 无 → 继续
  3. 切到/创建 draft/<slug>-<timestamp> 分支
  4. 写入文件
  5. git commit --author="<user email>" -m "docs: update <slug>"
  6. git push origin draft/<slug>-<timestamp>
  7. 返回 { commit_hash, branch }
```

### 7.3 冲突弹窗

```
前端收到 409:
  弹窗:
    "文件已被 <author> 修改于 <time>"
    [ 查看差异 ] [ 用我的覆盖 ] [ 放弃我的改动 ]
```

- **查看差异**：显示 diff（用 `diff2html` 或类似库）
- **用我的覆盖**：`base_commit` 更新为最新 → 重发保存
- **放弃我的改动**：丢弃本地，加载最新

**P0 不做三方合并**。要么用你的、要么用他的，二选一。

### 7.4 Web 提交审核

```
用户点击"提交审核"
  ↓
POST /api/docs/submit-review { slug, branch }
  ↓
后端:
  1. 用 octokit 在 GitHub 上创建 PR: draft/<slug>-<ts> → main
  2. 写入 review_tasks(source='web', pr_number=<pr>)
  3. 返回 PR URL
```

### 7.5 工程师提 PR

```
工程师本地:
  git clone joymaas-docs
  改文件
  git push origin feature/xxx
  在 GitHub 上开 PR: feature/xxx → main
  ↓
GitHub webhook 触发 → POST /api/webhook/github
  ↓
后端:
  1. 解析 PR 事件
  2. 写入 review_tasks(source='github_pr', pr_number=<pr>)
  3. 通知审核者(可选,P0 先不做)
```

### 7.6 审核队列（合并两种来源）

后台"审核队列"页面查询 `review_tasks` 表，Web 提交和 PR 提交显示在同一列表，区分标签。

```
审核队列
─────────────────────────────
[Web]  快速开始v2  by leah   [查看] [通过] [驳回]
[PR#45] chat API 参数补充  by zhangsan  [GitHub↗] [通过] [驳回]
[Web]  错误码补充  by wangwu  [查看] [通过] [驳回]
```

- **[查看]**：Web 提交的显示 diff（本地生成）
- **[GitHub↗]**：PR 的跳到 GitHub 页面
- **[通过]**：调用 GitHub API merge PR → 更新 review_tasks.status = 'merged'
- **[驳回]**：关闭 PR，写入 rejection comment

### 7.7 发布

**通过审核 = merge PR to main**。merge 后：

1. GitHub webhook 触发 push 事件到 `main`
2. 触发 Next.js 构建（P0 可以是 `curl` 一个 build endpoint，P1 用 CI/CD）
3. 构建产物部署到静态托管

## 9. OpenAPI 自动生成（P0 新增）

### 9.1 输入

`content/api-spec/openapi.yaml`（工程师维护）

### 9.2 输出

构建时执行 `apps/site/lib/openapi-to-mdx.ts`：

- 遍历 spec 中的 endpoints
- 为每个 endpoint 生成 `content/api/<endpoint-slug>.mdx`
- 生成内容：
  - Frontmatter：`source: openapi, title, description, slug`
  - Endpoint 元信息（方法、路径）
  - `<Params>` 参数表
  - 请求示例（多语言 `<CodeTabs>`）
  - 响应示例
  - 错误码骨架

### 9.3 人工补充

自动生成的 MDX 底部预留一个可编辑区：

```mdx
{/* @manual-section-start */}
## 使用场景

（人工补充：什么场景下用这个接口）

## 注意事项

（人工补充）
{/* @manual-section-end */}
```

- 后续重新生成时，`@manual-section-*` 之间的内容保留
- 结构化区域（`<Params>` 等）每次覆盖
- Web Editor 打开这类文档时，结构化区域**只读**，散文区可编辑

## 14. Claude Code 执行守则

1. **不问"要不要顺便做 X"**。范围钉死在 §2。
2. **不写占位代码**。每次提交端到端能跑。
3. **不造名词**。定位、组件名、文案照抄本文档。
4. **不写多余注释**。README 只写"怎么跑起来"。
5. **每周交付**：做完的项、下周计划、阻塞项。

8. **后台改造增量做**，不重写。
